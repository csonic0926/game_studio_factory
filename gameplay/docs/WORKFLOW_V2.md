# Gameplay v2 capability

Process source: `factory_core/docs/WORKFLOW.md`. Initialization, product adoption,
project-owned adapters, UI realization and observation tools remain available
under their existing CLIs and arguments. Missing adapters are initialization
work, not permission to invent project rules.

Inspect current task and gaps before advancing progression. Repair an evidenced
player-visible break first unless the USER explicitly defers it. Reuse the
frozen approved design for a mechanical repair; changed player work/outcomes or
scope require new complete-design review and a human decision.

The one complete package includes OBJECTIVE_GAMEPLAY.md, its expected experience
and complete playable table, the Studio causal graph when applicable, concrete
current-scene interaction contract and storyboards, adopted project standard,
required composition artifacts, costs/obligations/recovery, all alternatives,
hypotheses, red lines and acceptance requirements. Project standards are real
adopted authorities, not inferred from habits or replaced by generic questions.

Card excerpts and consequences come directly from this package. Both boundary
reviews check full-design -> human-view non-expansion and view -> full-design
completeness. The primary agent remains the spec/production author. Production
plans bind exact design and add only bounded execution/dependency/UI details.
A `factory_checkpoint.v2` design-verdict reference selects the v2 gate in
`design_gate.py`; legacy references retain legacy validation. The v2 gate
requires the current authorized checkpoint and exact objective hash, checks
content dependency freshness and invokes graph, project-standard/composition
and interaction validators. It never fabricates separate legacy reviewer ids.

UI changes still require `UI_PRODUCTION_WORKFLOW.md`: repo layout grammar,
state refresh, scene/lifecycle, input/layers, theme/fonts/localization and
accepted visual grammar. Runtime observations still use
`RUNTIME_OBSERVATION_AND_ACCEPTANCE_CONTRACT.md`; keep designed, implemented,
observed and accepted claims separate. A passing plan is not gameplay acceptance.
Runtime acceptance and baseline promotion are not bypassed by the v2 design gate.
